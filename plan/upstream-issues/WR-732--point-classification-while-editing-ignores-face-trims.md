#### WR-732. A point classification while the B-rep is edited ignores the faces' trims

- **Severity:** Wrong result
- **Area:** Topology
- **Location:** `source/SMLib/src/SmTrimSrfCache.cpp:186`, `SmTrimSrfCache::BuildTree` (def. `:132`); `source/SMLib/src/SmSurface.cpp`, `SmSurface::CacheMakeOrValidate` (def. `:5784`). Rust `surface::trim_srf_cache::TrimSrfCache::build_tree_body`, `query::brep::ray::face_surface_cache`.
- **What happens:** `BuildTree` skips implanting a face's UV trim curves while its B-rep has `m_bEditingEnabled` set ("face data structure may be in an intermediate state"). The tree it builds then is the untrimmed surface's. A point classification (`SmBrep::ClassifyPoint` and its ray casts) that builds a face's cache while editing therefore tests rays against the whole surface. Upstream's answer is right only when `CacheMakeOrValidate` reuses a tree built before the edit. A face whose trims changed mid-session, or one with no cache from before the edit, is classified as its untrimmed surface.
- **Trigger:** A ray classification while editing is on. Issue #2365's fillet session trims with editing on. The port builds each ray's face cache afresh (upstream's cache lifetime is not ported), so there points inside a 40 x 16 x 10 bar joined to an R8 x 20 post classify as outside. The ray's line/surface intersection is where the tree counts: a ray meets a curved face's surface where the face is trimmed away (inside the bar, the post's cylinder continues). A planar face's hits and a point on a face are classified by the face's loops, which are current.
- **How found:** PR #2503, while porting the cache lifetime for #2365's open-hole test.
- **Confirmed:** The skip is in the C++ source as quoted. The mid-session cases above were run in Rust only, not against the C++ build.
- **Construction change:** Under `UpstreamFixes::brep_ray_classifies_current_trims` (off by default), while editing, the ray's tree of a face whose loops close is built with the face's current trims implanted (`CacheFace::implants_while_editing`), and no kept cache is reused. A loop closes when each edge use ends where its successor starts; vertices still being merged by a stitch's glue meet within their tolerances. Such a face whose trims then fail to implant, or for which the factory falls back to the plain surface cache, is `SolidError::FaceTrimsUnavailable` naming the face (no test reaches this). A face whose loops are open mid-edit (an edge use without a start, one ending away from its successor's start, or one naming a deleted entity) has no boundary yet and keeps upstream's untrimmed tree. Refusing it instead failed 15 fillet tests that turn every flag on (`issue_2223_section_end_trim_at_creases`, `issue_2364_alpha1_ends`, `wr696_fit_sizes`, `wr707_rounds_running_off_their_faces`): the fillet session classifies against such faces and builds with upstream's answers. Outside editing, nothing changes. Regression tests: `crates/solidcore/tests/brep_query_cache_lifetime.rs`.
