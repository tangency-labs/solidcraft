#### WR-673. `TrimExtendedEdge` can take an open edge's first trim point again, as its twin across a closed curve's seam, so a sphere cap's two-edge rim offsets with a loop gap
- **Severity:** Wrong result
- **Area:** Offset
- **Location:** `source/SMLib/src/SmOffsetGeometryCreation.cpp:1318-1340`, `SmOffsetGeometryCreation::TrimExtendedEdge` (def. `:878`), the search for the solution closest to the base vertex. For the second trim point it refuses only `SM_ARE_SAME(rSol.m_vStart[0], sTrimIvl.GetMin())` (and the same for `m_vEnd[0]`): the first point's parameter, not the first point.
- **What happens:** a sheet's rim half lifts onto the whole offset circle, a closed curve. At the half's second vertex the only solution can be the coincident range the other rim half's offset (the same circle) gives. Its start is the first trim point and is refused; its end is the first point's twin across the circle's seam (another parameter, the same point) and is taken. One half's offset edge then gets the whole circle, the other a zero-length interval, which is culled, and the offset loop has a gap. With the fork's loop-gap closing (`offset_closes_loop_gaps`, WR-578) the thicken fails with `SM_ERR_OFFSET_EDGE_VANISHES` (1043), or in the merge (`relate`, 1001) on SolidCraft's sheet. Without it the result is no manifold solid (volume -627.4 out, 0 in, against 331 pi/3 and 271 pi/3).
- **Trigger:** the r 10 sphere's face above z = 5 taken alone and thickened by 1 or -1 (`SmApiShellBrepFull`, create offset solid, extended convex edges, merged results), when its rim is two half circles placed against the seam as the sphere intersected with a box over z >= 5 turned 90 degrees about z leaves them (vertices (+-8.66, 0, 5), seam end (8.66, 0, 5)), or the sphere turned 90 degrees less the box below (vertices (8.66, 0, 5), (0, 8.66, 5)). tangency-labs/solidcore#2174 (after #1502). The rim shapes of `issue_1502_*` take the right point without the fix.
- **How found:** SolidCraft report #2174; the fix is the fork's tangency-labs/smlib@7ee0876 (written for #1502): an open edge's second trim point must lie more than 10 times the approximation tolerance from its first.
- **Confirmed:** yes, against the pinned C++ on the repro's sheet (`fixtures/offset.offset_executive_p2/issue2174.json`, read from a Rust-written ASCII `.smb`): inward the C++ result agrees with the port's default (no manifold solid). Outward the pinned C++ crashes (SIGSEGV inside `SmApiShellBrepFull`; where was not traced, no debugger on the machine), so that direction has no difftest case. The port at its defaults returns a non-manifold body there.
- **Rust port:** behaves as upstream by default. With `Kernel::fixes.offset_open_edge_second_trim_point`, `trim_extended_edge` (`crates/solidcore/src/offset/offset_geometry_creation.rs`) also refuses, for an open edge's second trim point, any solution point within `10 * this_approx_tol_3d` of the first trim point, as the fork does. The half's offset edge then has no second trim point and is left to the merge.
  Tests: `crates/solidcore/tests/issue_2174_cap_rim_two_edges.rs`. With the flag (the issue's preset, and with only this flag on the defaults) the three sheets (the repro, the turned sphere less a box, SolidCraft's sheet) thicken both ways to manifold solids clean at `check_brep` level 2, within 1.3e-8 of 331 pi/3 and 271 pi/3. Without it, under the issue's preset, the repro fails with 1043 both ways; at the defaults it is no manifold solid.
