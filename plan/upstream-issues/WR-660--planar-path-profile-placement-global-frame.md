#### WR-660. A planar-path sweep rolls its profile when the whole setup is tilted out of XY, changing its shape and first-point volume
- **Severity:** Wrong result
- **Area:** Sweeps and primitives
- **Location:** `source/SMLib/src/SmPrimitiveCreation.cpp:5596`, `PositionProfileCurves`, particularly `:5639-5647` (profile normal to global X) and `:5653-5663` (global Z crossed with the start tangent, global Y fallback). Called at `:5884` by `CreateSweepAlongPlanarPath`.
- **What happens:** positioning is relative to the global axes rather than the path plane. First the shortest rotation takes the profile normal to global X; then a frame built from the tangent and global Z places it at the path start. Their composition does not commute with a rigid rotation of the setup. The profile rolls about the path even when already centred on it. With a first-point anchor, the roll also changes the radial offset and volume. A world-aligned bounding-box midpoint is another pose-dependent part of this placement for asymmetric profiles. Changing only the final frame normal does not address the preceding profile-normal rotation.
- **Trigger:** a 4 x 4 square with ordered vertices `(18,0,-2)`, `(22,0,-2)`, `(22,0,2)`, `(18,0,2)` and a radius-20 quarter arc from 0 to 90 degrees about the origin in XY. Rotate both profile and path by 30 degrees about X. `SmApiCreateSweepAlongPlanarPath`, both caps, with either profile-centre or first-point anchoring.
- **How found:** private ordinary-operation sweep, `matrix/cpp/cppmatrix.cpp` operation `pps`, and `matrix_chains.rs` planar-path-square cases; traced in the pinned C++ and its Rust port.
- **Confirmed:** yes, existing C++ driver, `cppmatrix - pps 0:1`, `30:1`, `0:0`, `30:0`. All return success, six faces, twelve edges, manifold, zero check failures. Centre anchor: volume 502.655040 flat / 502.654666 tilted (numerical sweep/quadrature estimates); after undoing the tilt, Z bounds grow from `[-2,2]` to `[-2.732051,2.732051]` and radial maxima from 22 to 22.732051. First-point anchor: volume 452.388984 flat / 484.256217 tilted; canonical Z bounds `[0,4.000001]` / `[0,5.464102]`. The private sweep also found a point 0.1 above the flat top classified inside the tilted result.
- **Related:** WR-407's `sweep_frame_on_planar_path_normal` changes the later curve-sweep transport frame, not this placement; it does not fix the roll, and it removes the small drift the fix leaves. WR-632 concerns ignored placement statuses; UB-113 concerns path casts. Neither fixes this defect.
- **Rust port:** default retains pinned C++ placement. The opt-in `Kernel::fixes.planar_path_profile_in_path_frame` runs the unchanged placement of every piece in the whole path's one XY frame (Y along its start tangent, Z along its signed plane normal, `ComputeCrvsNormal` of all its pieces), then maps the profiles back. One frame for all the pieces matters: a frame per piece leaves a straight piece rolled beside an arc that is not, and the mitre between them cuts the sweep to volume 0. The frame needs no global-axis fallback for perpendicular path planes. In or parallel to XY, either normal, the exact upstream arithmetic remains. A straight path retains upstream placement: it does not determine a plane. Public reachability: `sweep::api_brep::create_sweep_along_planar_path` → `PrimitiveCreation::create_sweep_along_planar_path` → `create_sweep_along_planar_path_owned` → `position_profile_curves_impl`; the standalone public `position_profile_curves` also reaches the guard. Regression source: `crates/solidcore/tests/wr_660_planar_path_pose.rs` (both anchors, X/Y/general rotations, vertical/opposite planes, translations, boxes and classification; a line and an arc in either order). With the flag, every tested pose is within 1e-4 of the closed-form volume (160 pi centred, 144 pi first point; first point at 30 degrees about x, flag off 484.256217, flag on 452.389004), and the bounding boxes, moved back, agree to 5e-3, against a roll of 0.73. What is left is the sweep's own pose-dependent fit (at most 4.6e-5 of the volume, 3.3e-3 of the box): with `sweep_frame_on_planar_path_normal` (WR-407) on too, the boxes agree to 1e-5. Forcing the flag off fails the invariance tests.
- **Paths of several pieces need both flags.** A line and a quarter arc, in either order, for both anchors and seven tilts, with `sweep_frame_on_planar_path_normal` on as well: every volume within 1e-4 of the closed form (160 pi + 320 centred, 144 pi + 320 first point) and every box within 1e-3 of the flat body's. With this flag alone, an arc-then-line path tilted 30 degrees about y, or about a general axis, still has volume 0. With both flags off, an arc-then-line path tilted 30 degrees about x has volume 0 and a line-then-arc path is rolled (822.654314, z extent 2.732); these two-piece numbers are the port's, not run on the C++. A path whose pieces cancel to no plane normal (`ComputeCrvsNormal` fails) keeps upstream's placement; that case was not tested.
