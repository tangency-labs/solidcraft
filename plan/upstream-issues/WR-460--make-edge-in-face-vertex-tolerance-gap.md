#### WR-460. `MakeEdgeInFaceWithVU` leaves a vertex tolerance below twice its gap to the new edge's end
- **Severity:** Wrong result
- **Area:** Topology, attributes, solvers
- **Location:** `source/SMLib/src/SmBrep.cpp`, `SmBrep::MakeEdgeInFaceWithVU` (`:12242`), its tolerance tail (`:13457`, "recompute modified vertex tolerances"); `SmVertex::RefreshTolerance` (`source/SMLib/src/SmVertex.cpp:2313`). The check that refuses the result is `SmBrep::ValidateAndUpdateTolerances` test 0/2 (`SmBrep.cpp:33327`), reached from `AssertValid`.
- **What happens:** `AssertValid` holds an edge/vertex gap to half the vertex's tolerance. `MakeEdgeInFaceWithVU` calls `RefreshTolerance(FALSE)` on both end vertices, which with `SM_USE_OLDTOL` sets the vertex to its own tolerance (`SmTol::GetZoneTol3d` of a topology object is its tolerance): nothing is recomputed. When the caller gives the UV trim curve (an intersection does), no curve drop sets the edge tolerance from the gap either, so an edge may end up to the vertex's full tolerance away (the debug-build assertion in the same function allows that) and the body is refused. `UpdateVertexEdgeIntervals` (`:32981`) and the repair branch of `ValidateAndUpdateTolerances` set a vertex to twice its gap.
- **Trigger:** SolidCraft rig `booleans/steel-026-chs-k-joint-overlapped-braces`: a CHS 88.9x5 chord along x, two CHS 48.3x4 braces at +-45 deg coped to it and overlapping each other, joined. The braces' intersection curve lies in the plane x = 0 and ends at the vertex where both braces meet the chord, which the solver placed 5.26e-6 off that plane: the edge ends 5.44e-6 from the vertex, whose half tolerance is 5.42e-6 ("Edge/Vertex gap across Edgeuse start larger than tol (offset=5.4413729e-06, tolerance=5.4235813e-06)"). The edge is not mis-trimmed: its end is its curve's natural end and the curve's nearest point to the vertex. A first `AssertValid` raises the tolerance as a side effect (`FindInfiniteRegion` building UV trims), so a second check passes on the same body.
- **How found:** SolidCraft regression rig; the three operands dumped from SolidCraft and replayed on the fork's C++ build, with the vertex's `SetTolerance` and `SetPoint` traced (backtraces) through `SmMerge::ManifoldBoolean`.
- **Confirmed:** yes, on the C++ build (the fork, tangency-labs/smlib@5af7070 with the WR-265 change, x86-64 Linux, g++): growing each end vertex's tolerance to twice its gap to the new edge's end, after `RefreshTolerance`, makes the check pass with the same volume; the pinned `c9c5979` has the same tail. Fork test `capi/tests/booleans.cpp` `overlapped_k_joint` fails without it.
- **Rust port:** opt-in `Kernel::fixes.new_edge_vertex_tolerance_covers_gap` (`UpstreamFixes`, default `false`, upstream behaviour). With it, `make_edge_in_face_with_vu` (`crates/solidcore/src/topology/brep/p9.rs`) follows the fork's fix: after `refresh_tolerance`, `vertex::set_tolerance(.., 2.0 * gap, true, ..)` for each end vertex. Tests in the same file: `new_edge_grows_its_vertices_tolerance_to_twice_the_end_gap` (field on; a box face's diagonal given with its UV trim, overshooting its far corner by 0.7 of the corner's tolerance) fails without the change, and `new_edge_keeps_its_vertices_tolerance_by_default` (field off: the tolerance stays, as C++). The fix was first unconditional; it then changed the `intersect.curve_class_p6` difftest cases `imprint_face_split_f0` and `imprint_face_split_f2` (`values.out[159]`: C++ 0.059022494374947436, Rust 0.11804298874989479), so it is opt-in (as WR-255, WR-259, WR-265; suggested in the #870 review). With the default, `intersect.curve_class_p6` and `topology.brep_p9` match C++. Callers that need the fix (SolidCraft) set the field.
