#### UB-275. `SmPolyMerge::ManifoldBoolean` goes on with deleted PolyEdges when `SmPolyIntersector::FixGaps` fails after combining vertices
- **Severity:** Crash / undefined behaviour
- **Area:** Booleans
- **Location:** `source/SMLib/src/SmPolyMerge.cpp:1258`-`:1265`, `SmPolyMerge::ManifoldBoolean` (def. `:1122`): the common edge and vertex lists are gathered again only when `FixGaps` returns `SM_SUCCESS`; the stale list is then read at `:1399` (`pFace->IsMarked(eBrepMarkType)`). `source/SMLib/src/SmPolyIntersector.cpp:1137`-`:1161`, `SmPolyIntersector::FixGaps` (def. `:1058`): both `CombineCoincidentVertices` calls run before any `RemoveRelationship`, and only the Brep's deleted PolyEdges are unmated (`:1153`-`:1159`). The failure after the combine is the `SER( eStat )` of `MakeEdgeInFace` while connecting the dots (`:1214`, `:1224`).
- **What happens:** `FixGaps` first merges coincident single vertices, which deletes PolyEdges, then joins the remaining single vertices with new edges. When a `MakeEdgeInFace` there fails, `FixGaps` returns the error with `rbModifiedTopology = TRUE`. `ManifoldBoolean` ignores the status (`(was SER [B105])`) and, because the status is not `SM_SUCCESS`, keeps the common edge list it gathered before the call. That list still holds the deleted PolyEdges, and the face classification dereferences them. In the reported run the freed memory had been reused by a new PolyEdge without a face, so `SmTopology::GetMark` ran on `this == NULL`. Separately, `FixGaps` never removes the relations of the Other PolyBrep's deleted PolyEdges, and when the Other's `CombineCoincidentVertices` fails it also leaves those of the Brep's deleted vertex and PolyEdges, so the relation maps keep pointers to deleted records.
- **Trigger:** prog_test `tessellation` suite, `my_poly_boolean_regression` -> `my_test_ppu` (`SM_PBO_UNION`) on a pair of solids from `TestFiles/pt_TestFiles/Solids/box_cone_grid.smp`, with tessellations refined to the chord tolerance (the fork's fix for tangency-labs/solidcore#390). Stock 1.0.1 tessellations do not make `FixGaps` fail there.
- **How found:** crash in the SolidCraft fork's prog_test run (tangency-labs/solidcore#732, filed by jyviko): `SmTopology::GetMark(this=0x0)` <- `SmTopology::IsMarked` <- `SmPolyMerge::ManifoldBoolean` `SmPolyMerge.cpp:1399`. At the crash `FixGaps` had returned 1001 with `bModifiedTopology = TRUE`, and common edge 44 of 456 had no loop and no vertex.
- **Confirmed:** in the fork build (backtrace above); not at the pin, where the stock tessellation does not reach the failing `FixGaps`. The reference build here is not run on it (no shim reaches the polygon Boolean).
- **Fix (fork, "SMLib: a polygon boolean whose gap fixing fails reads no deleted PolyEdge"):** `ManifoldBoolean` gathers the common edges and vertices again (and takes a new mark) whenever `bModifiedTopology` is set, whatever the status; `FixGaps` sets `rbModifiedTopology` before the first combine and removes each PolyBrep's deleted PolyVertex and PolyEdge relations right after that PolyBrep's combine (the Other's through `GetBrepMate`).
- **Rust port:** not affected; nothing to fix. The polygon Boolean (`SmPolyMerge.cpp`, `SmPolyIntersector.cpp`) is outside the port: no in-scope root reaches it (`plan/closure.md`, Provably unused), it belongs to no unit in `harness/callgraph/units.json`, and `query.poly` ports only the PolyBrep queries. The B-rep counterpart has no continue-after-failure path: `SmMerge::ManifoldBoolean` `SER`s on `SmTopologyIntersector::FixGaps` (`SmMerge.cpp:3029`), and the port propagates it with `?` (`crates/solidcore/src/boolean/merge/p4.rs`, `intersector.fix_gaps(...)?`). Its arenas address records by typed ids, so a stale id is a lookup that fails, not a freed read. If the polygon Boolean is ever ported, its porter should take the fork's fix with it (unconditional, crash class). Findings: `plan/findings/general--polygon-boolean-fixgaps-failure-not-ported.md`. Refs tangency-labs/solidcore#732 (the WR-307 promised in its triage comment was never filed; this is that record).
