#### UB-260. `SmMakeCurveBlendSIH::SmoothOutIntersection` dereferences the fillet geometry's NULL centre line on the first flush
- **Severity:** Crash / undefined behaviour
- **Area:** Blending and fillets
- **Location:** `source/SMLib/src/SmFilletSolver.cpp:8202`, `SmMakeCurveBlendSIH::SmoothOutIntersection` (def. `:8157`); called from `SmFilletIntersector::FlushCurve` (`source/SMLib/src/SmFilletIntersector.cpp:1569`).
- **What happens:** With an `SmMakeCurveBlendSIH` installed on the executive (`SetSelfIntersectionHandler`), every `FlushCurve` calls `SmoothOutIntersection` with the geometry `FlushCurve` is about to fill. On a traced section's first flush that geometry has no centre line yet (`m_pCenterLineCurve == NULL`), and `pFilletGeom->GetCenterLineCurve()->GetNaturalInterval()` reads through `NULL` (no `NER`). Every flush seen in testing either fails the earlier `NER(pFace1)` (rails without an original face, status `SM_ERR_NULL_POINTER`) or reaches this dereference and segfaults, so the method's joining code is never reached. The same function also reads `m_vRails[i]`, the rail's primary edge use, its mate, the mate's UV trim curve, the rail curve and `sSolutions[0]` of `GlobalCurveSolve` without checks. The Rust port returns `InvalidInput` at each of these.
- **Trigger:** `SmApiFilletEdges` set-up with `SmMakeCurveBlendSIH(1.0)` installed, e.g. `Fillet/nurb_box.smb` edge 0 or `Fillet/corner_box.smb` edge 11 at radius 0.5 (any traced fillet whose rails have original faces). No SM_API entry installs this handler; `smFilletTest.cpp:4739/4841/4926` declare one (`pSIH`) but install the surface-blend `sSIH` instead.
- **How found:** shim probe while porting the handler (an `SmMakeCurveBlendSIH` subclass logging each call and the geometry's pointers before delegating).
- **Confirmed:** yes, C++ build segfaults inside `SmoothOutIntersection` (the subclass logs entry and no return); the `NER` path is case `curve-sih-box_diff_cyl-all-edges-r0.1` of `blend.fillet_executive_p3`.
