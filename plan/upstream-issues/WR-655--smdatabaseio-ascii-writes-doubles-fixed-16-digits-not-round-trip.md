#### WR-655. `SmDatabaseIO` ASCII writes doubles as fixed `%.16f`, which does not round-trip `|x| < 1`
- **Severity:** Wrong result
- **Area:** File reading
- **Location:** `source/SMLib/src/SmDatabaseIO.cpp:170`-`171`, `SmDatabaseIO::OpenFileForWrite` (`SM_ASCII`): `m_pStreamOut->setf(SM_IOS::fixed); m_pStreamOut->precision(16);`. Every ASCII double that `SmBrep::WriteToFile` / `SmBrepData::WriteToFile` and the `WriteToDB` records write goes out through that stream's `operator<<(double)`, i.e. glibc `%.16f`. (`SmDatabaseIOStream` callers set their own stream format; the binary mode writes the 8 raw bytes and is lossless.)
- **What happens:** `%.16f` keeps 16 digits after the decimal point. That is 17 or more significant digits for `|x| >= 1`, enough to read the same double back, but at most 16 for `0.1 <= |x| < 1` and fewer still below `0.1`, so a value there can read back as a neighbouring double, or as a coarser one the smaller it is. Measured on 100 000 uniform samples per range, by `%.16f` then a correctly rounded parse (glibc `strtod`, as libstdc++'s `operator>>` uses): `[1, 1000)` round-trips 100%; `[0.1, 1)` fails 24.6%; `[0, 0.1)` fails 91.9%. Example: `0.30000000000000004` (`0.3` plus 1 ULP) is written `0.3000000000000000` and read back as `0.3`. UV parameters, weights and small coordinates live in that range, so an ASCII write then read of a model moves them: a trim point 1 ULP off was enough to flip a near-singular Newton step downstream (#1485, EU67), and the read-back volume of a sphere drifts by 1.3e-5 relative (below).
- **Trigger:** any ASCII save and reload (`WriteToFile(..., SM_ASCII, ...)` then `ReadFromFile(..., SM_ASCII)`) of geometry with doubles of magnitude below 1 that need 17 significant digits.
- **How found:** #1485 (an ASCII round trip of a Rust Boolean union moved EU67's UV trim point by 1 ULP), then reading the writer; and the earlier finding `plan/findings/corpus.parity--ascii-round-trip-volume-drift-is-upstreams-own-2026-10-23.md`.
- **Confirmed:** yes with the C++ build for the loss itself: in that finding the C++ child wrote `Solids/sphere.smb` with `SmBrep::WriteToFile(path, SM_ASCII, TRUE, FALSE, 0.0)` and read its own file back with volume `523.5923997299045` against `523.5990772283121` as first read (area `314.160106233197` against `314.15938308003854`). The per-value example and rates are by reading (the glibc `%.16f` semantics), not a C++ case.
- **Rust port:** writes the same bytes on the default path: `crates/solidcore/src/topology/database_io.rs:1085` (`fixed16`, `format!("{x:.16}")`, with glibc's `inf` / `-inf` / `nan` / `-nan`), used by `DatabaseWriter::out_f64` (`:1173`) for every ASCII record; the reader parses correctly rounded (`:653`). The finding above shows the two writers' files byte-identical. A round-tripping format (`%.17g`, or the shortest round-trip form) could only be an opt-in, never the default, since the default must match C++'s bytes; none is implemented.
- **Comparisons:** a comparison that needs bit-equal values (port against C++, or a value against its own reload) must use a binary `.smb`, or no file round trip at all. An ASCII reload is lossy on both sides by design.
