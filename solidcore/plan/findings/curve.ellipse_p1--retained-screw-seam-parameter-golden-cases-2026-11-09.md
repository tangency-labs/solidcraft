# curve.ellipse_p1 and surface.cone_p1: the 192 golden cases the retained screw sweeps' seam-parameter change moves (2026-11-10)

- **Units:** 13 units, chiefly `curve.ellipse_p1` (`PolarConversion`) and `surface.cone_p1`
  (`Cone::evaluate_point`, `convert_uv_from_nurbs_to_step`) with their `surface.surface_p2` twins
  (`common_cone_*`, the same inputs through `Surface`); PR #13891.
- **Change:** #13891's thread commit keeps the angle of a NURBS parameter near a closed curve's
  seam instead of setting it to the seam (`PolarConversion`, `Ellipse::parameter_angle`), maps the
  exact NURBS ends to the analytic domain's own ends (0° and 360°, not 0° twice), and evaluates a
  cylinder through that angle. The follow-up commit computes an angle next to an NURBS end
  (within 1e-6 of the interval) from the end's exact angle plus `atan(q) ≈ q − q³/3` with
  `+ − × ÷` only, and returns the end exactly when the offset is within the evaluation's rounding
  (`Ellipse::near_end_parameter_angle`). Every case below moves for these reasons.
- **How measured:** on one machine (macOS, Apple silicon), this branch and `main` `126e91f95b`
  were each run on every unit (`--all`) into scratch goldens on the same machine, so platform
  rounding cancels, and compared case by case with the goldens' own rule (1e-9 relative, per float
  and per block). Each moved case was checked against an independent reference:
  - a cone's or ellipse's NURBS form is exact, so an answer's error is its distance from that
    form's point at the same parameter (relative to the point's size);
  - where that form is not a valid reference (an extrapolated or unbounded v map, or coordinates
    of 1e5 whose rounding exceeds the offset), the angle was checked instead against the same cone
    at the origin, whose polar parameter maps to the same angle (3.2411387e-10° for 1e-12 of the
    canonical 4-span domain);
  - a surface's or body's state was read field by field.
  Values per parameter came from temporary debug output on both trees, since removed.
- **Recorded here:** 190 cases, each re-recorded from this machine's run only where `main` on this
  machine reproduces the Linux-recorded value (within the goldens' tolerance), and only the fields
  that moved beyond it. Two cases, `review_unb30r1_ep[1000.0, -1000.0]` and its `surface_p2` twin,
  carry the Linux CI value (`main` here already differs from Linux there). With all goldens
  re-recorded, the cases this branch fails on this machine are exactly the 1,007 cases `main`
  fails here (Mac-only rounding, other units); Linux CI is the check of record.
- **Not recorded:**
  - `topology.assert_valid` `l2_file_Solids_extrusion_tests` and `l2_file_Solids_off_extrusion_tests`:
    the seam change moved one vertex gap there on Linux (v1 at (8, 10, 0), on a quarter-circle face
    whose projected u is 2.2e-14 inside its NURBS end: 3.55e-14 → 1.78e-15, block 7.28e-14 → 3.91e-14),
    and the end snap of the follow-up commit returns it to `main`'s 3.55e-14 (reproduced here, where
    their vertex gaps match Linux; only their `edge_test13` differs here, on `main` too). Nothing to record.
  - 14 cases the seam change had moved and the follow-up commit returns to `main`'s values, so their
    goldens are `main`'s again: `surface.cone_p1` and `surface.surface_p2` `r3_01121`, `r3_04449`,
    `r3_16481` and `r3_36705` (far cones whose atan2 followed the NURB point's rounding; for
    `r3_36705`, a 1e-4 cone 1e5 from the origin, −1.5e-5° where the exact angle is 3.24e-10°, moving
    the point 8.7e-8: that was a regression, wrongly called equivalent in this file's first version,
    and is fixed by the snap), the four `surface.surface_p2` `rev_step_inv_torus_*_nonplanar_guess1`
    (7.9e-13 and 5.7e-13 back to 0), and `topology.assert_valid` `l2_file_Solids_OffsetBoxCylOnCorner_tests`
    and `l2_file_Solids_OffsetBoxWithBoss_tests` (gaps back to 1.46e-14 and 1.63e-14).
  - In-tolerance moves: on this machine the branch also moves cases within the goldens' 1e-9
    relative tolerance (exact bits differ, the comparison passes), which are not recorded:
    `surface.cone_p1` 62, `surface.surface_p2` 62, `curve.ellipse_p1` 28, a few elsewhere (heal,
    corpus parity, fillet; 20 in all). Before the follow-up commit these were 74, 76 and 29; the
    Windows run's 75 and 77 are those plus the `review_unb30r1_ep` pair, and two of its examples
    (`r3_01633` 360 → 359.9999999996759, `r3_01373` 230078.667282316 → 230078.66728231602) are
    bit-identical here.
- **Platform:** the recorded answers are now libm-free where the angle is concerned:
  - a clamped or exact NURBS end maps to the domain end exactly (31 ellipse and 33 cone cases, and the 33 cone twins);
  - an angle within 1e-6 of an NURBS end uses `+ − × ÷` and the rounding snap, so it is the same on
    every IEEE platform (the interior near-seam corrections);
  - elsewhere the conversion still uses atan2, as `main` does, and every evaluated point uses sin and
    cos of its angle (a seam point at 360° carries `sin 2π = −2.4492935982947064e-16`, the correctly
    rounded value).
  `main` itself is not platform-independent: on this machine it differs from its Linux goldens in
  1,007 cases beyond the tolerance (Apple libm against glibc).
- **Verdicts:** 86 corrections (the old answer was wrong: full turns collapsed to zero length with
  NaN knots, near-seam parameters moved onto the seam by up to 5.7e-9 relative, a missed second
  solution), 104 equivalent answers (the same point written differently: 0° vs 360° at a seam, a
  clamped parameter at its own end of the domain, an exact 0 vs a sin 2π residue, a circle traced
  the other way, gaps moving within rounding, the same fillet refusal with a different status), and
  2 rounding-level losses (`r4_09551` in both units: an angle 2.8e-15° further from the nearest
  origin reference, 8e-17 at radius 1, below the coordinates' ulp). No case is further from its
  exact reference by more than rounding.
