Updates: HANG-29

#### HANG-29 (update, 2026-11-02). The `query.face_p1` wrapper and runner refuse the overflow range before the B-rep ops
- **Trigger (nightly fuzz, runs 41190675541, 41299002064 and 41438521478, `query.face_p1` `fuzz00201`, `cpp: no result after 20 s` every night):** `CalculateBoundingBox` with `bTight` on a (1, 3) B-spline face (base `gen0502`) with the mutation `/brep/surface/bspline/net/0/1/2 = 1e+300`. Replayed alone on main `340782351` with the prebuilt v1.0.1 reference: no result in 180 s.
- **Location (gdb on the v1.0.1 reference, x86-64):** after the fixture export, in the op: `SmRegion::CalculateBoundingBox` -> `SmShell::CalculateBoundingBox` -> `SmFace::CalculateTightBoundingBox` -> `SmFace::PointClassify` -> `SmLoop::ContainsUVPoint` -> `SmLoop::GetUVCornerBoundaries` -> `SmEdgeuse::GetOrCreateUVTrimCurve` -> `CreateUVTrimCurve` -> `SmSurface::DropAndTrimCurve` -> `SmSurfaceDropCurve::DoTrace` -> `FindBoundaryStartPoints` -> `SmCurve::GlobalCurveIntersect` -> `GlobalCoincidenceChecker` (recursing). The HANG-29 path, reached from a point classification instead of the export.
- **Why the guard was missing:** the export (`topology.edgeuse_p1`) does not create UV trim curves for this block, so it returns; the hang is in the op itself, and `query_face_p1::eval` had no block check.
- **Rust port:** the kernel refuses the face itself, unconditionally. `query::face::p3::check_face_coordinates` returns `SolidError::InvalidInput` ("face geometry coordinate above 1e150 (HANG-29)") when the face's vertex points, the loose boxes of its edges or the loose box of its surface over its UV domain reach a finite coordinate above `limits::MAX_COORDINATE_MAGNITUDE = 1e150`. It runs at the entry of `query::face::p3::calculate_tight_bounding_box` (and so of the face, shell and region tight boxes of `query::face::p1`), `query::face::p1::point_3d_classify` and `query::face::p1::edge_curve_on_classify`. Loose boxes are not guarded, because upstream returns on them at 1e300. The difftest wrapper `query_face_p1::eval` refuses a block with a value above `topology_edgeuse_p2::MAX_BLOCK_MAGNITUDE = 1e150` for the `Box`, `Point3d` and `EdgeOn` ops, so the C++ side is a harness error (`FaceFu`, which `query.brep`, `geom.object` and `geom.tol` use through `query_face_p1::model`, only reads face uses and is unchanged). The runner's Rust side runs the kernel, whose refusal is the Rust outcome; `crates/difftest/tests/fuzz_corpus/query.face_p1.json` records both refusals.
- **Confirmed:** yes (no result in 180 s, reproduced alone; gdb backtrace).
- **Thresholds (measured by @Sloptimum on v1.0.1, reported on #1364, whose claim on this case they closed in favour of this guard; thanks):** on this face `SmFace::CalculateTightBoundingBox` does not return from a control point of 1e155 and returns at 1e154; the loose box and the default-argument box return at 1e300. `SmFace::Point3DClassify` and `SmFace::EdgeCurveOnClassify` on the same face do not return from 1e153. The `1e150` bound therefore leaves margin for all three ops. Without the guard the Rust port took about 18 s on the tight box, so the runner refuses the block on the Rust side too. Their unpushed version refused control points above 1e150 on both sides as well.
- **Regression tests:** `crates/solidcore/tests/issue_2393_face_query_coordinate_bound.rs` (the public kernel queries refuse a B-spline face with a control point of 1e300, in under 5 s, and 4e150; a bulge of 0.25 is not refused; without the guard the queries are not refused), `solidcore_ffi::units::query_face_p1::eval_tests::huge_block_values_are_refused_before_the_classifying_ops` (the FFI refuses `Box`, `Point3d` and `EdgeOn` before the C++), and `difftest::units::query_face_p1::tests::fuzz00201_huge_control_point_is_refused_on_both_sides` (the fuzz00201 input is refused on both sides; without the kernel guard the Rust side returns a box after 26 s).
