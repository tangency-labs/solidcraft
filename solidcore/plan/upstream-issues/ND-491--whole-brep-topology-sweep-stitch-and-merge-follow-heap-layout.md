#### ND-491. `SmTopologySweep::DoSweep` (whole B-rep): stitched and merged results depend on heap layout
- **Severity:** Nondeterminism
- **Area:** Sweeps
- **Location:** `source/SMLib/src/SmTopologySweep.cpp:971` (`DoSweep`, whole-B-rep branch: `sHCR.GetSilhouetteEdges(sSilEdges)`), which returns `SmHCR::m_pSilEdges->GetAllKeys` (`SmHCR.cpp:312`, an `SmMapPtrToPtr<SmEdge, SmEdge>`, i.e. a `std::unordered_map` keyed by edge address, ND-2). The silhouette edges are swept in that order, so the creation order of the swept topology, and with it the vertex and edge pairing order of the following `SmStitch::DoStitching` (`:1363`) or `SmMerge::PiecewiseMerge` (`:1346`), follows heap addresses.
- **What happens:** the same call on the same box returns different results in different processes: `SM_ERR` (1001) or success, or successes with different region/shell/face counts. Observed with `sc_sweep_topology_sweep_whole` (an `SmApiCreateBox` solid swept with all six target arrays NULL), each run in a fresh forked child after a different sequence of prior allocations in the parent, 200 runs per input (inputs `[length, width, height, kind (1 translation, 2 rotation), vx, vy, vz, angle_deg, stitch, merge, repetitions]`, rotations about the axis through the origin):
  - `[3,7,2,1,5,0,0,0,1,0,1]`: 180 success (1 region, 1 shell, 14 faces, 28 edges, 16 vertices), 20 `SM_ERR`.
  - `[3,7,2,1,0,-4,0,0,1,0,1]`: 187 with 1 region/shell, 13 with 2 (same faces, edges, vertices).
  - `[1e-3,2e-3,1e-3,1,0,0,1e-3,0,1,0,1]`: 164 with 3 regions/shells, 29 with 4, 7 with 2.
  - `[10,10,10,2,0,1,0,90,1,0,1]`: 146 success (15 faces, 25 edges, 12 vertices), 54 `SM_ERR`.
  - `[10,10,10,2,1,0,0,30,1,0,1]`: 196 with 1 region/shell, 4 with 2.
  - `[10,10,10,2,0,1,0,90,0,1,1]` (merge): 95 with 3 regions and 20 faces, 87 with 2 regions and 19 faces, 18 with 3 regions and 19 faces.
  The translations `[10,10,10,1,0,0,5,...]`, `[10,10,10,1,1,2,5,...]` and `[1e4,1e4,1e4,1,0,0,5e3,...]` with stitching, merging or both gave one result in all 200 runs.
- **Trigger:** a whole-B-rep `DoSweep` (no target arrays) with `m_bDoStitching` or `m_bDoMerge` whose silhouette is not symmetric enough for every visiting order to stitch or merge alike. No upstream caller reaches the whole-B-rep branch with a selection-free call except `SmApiNonManifoldSweep` / `SmApiNonManifoldRotationalSweep` without a selection.
- **How found:** the `sweep.topology_sweep` `whole_stitch_*` / `whole_merge_*` difftest cases: `[3,7,2,1,5,0,0,0,1,0,1]` returned `SM_ERR` inside a `cargo test` process and success in the difftest worker; reproduced by sweeping each input 200 times in fresh forked children while fragmenting the parent heap between runs.
- **Confirmed:** yes, on the C++ reference (Ubuntu x86_64 prebuilt, glibc): the same native call on the same input gives the outcomes above depending only on prior heap allocations. An uninitialised read was not separately ruled out (no valgrind or MSan build available), but every variant is consistent with the silhouette order: the Rust port, which sweeps the silhouettes in ascending edge id order, reproduces one of the C++ variants exactly for each input above (the majority one except for the 1e-3 box, where it is the 4-shell one).
- **Rust port:** `blend::hcr` keeps the silhouette edges in ascending id order, so the port is deterministic. The difftest compares the stable inputs and parks the six heap-dependent ones (`crates/difftest/known_mismatches/sweep.topology_sweep.toml`).
