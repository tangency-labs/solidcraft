#### HANG-29 (update, 2026-10-31). `SmApiTrimSurfaceWith3dCurves` reaches it; the `primitive.api_trim_ops` FFI refuses the trimmed surface's overflow range
- **New trigger (nightly fuzz run 41040730716, 2026-10-30, `primitive.api_trim_ops` `fuzz00254`, `cpp: no result after 20 s`):** `SmApiTrimSurfaceWith3dCurves` on the 4 x 4 net of `SmApiCreateSurface` (the `trim3d_net_surface` fixture: a flat 10 x 10 net trimmed by a radius-3 circle) with two mutations, control point 1 at `z = -2^63` and control point 8 at `y = 1e300`.
- **Location (gdb on the v1.0.1 reference, x86-64):** `SmApiTrimSurfaceWith3dCurves` -> `SmTrimmingTools::TrimSurfaceWithModelSpaceCurves` -> `SmTrimmingTools::CreateUVTrimCurves` -> `SmFace::CreateUVTrimCurves` -> `SmEdgeuse::GetOrCreateUVTrimCurve` -> `SmEdgeuse::CreateUVTrimCurve` -> `SmSurface::DropAndTrimCurve` -> `SmSurfaceDropCurve::DoTrace` -> `FindBoundaryStartPoints` -> `SmCurve::GlobalCurveIntersect` -> `SmCurve::GlobalCoincidenceChecker` (16 frames deep and still splitting) -> `DropPoint` -> `GlobalPointSolve`: the HANG-29 path.
- **Regime (per-call timing, release reference):** both mutations are needed: the `1e300` point on the flat net returns at once (0.03 s), and so does the lifted point alone. With the lifted point (any of `z = -10`, `-100`, `-1e5`, `-1e10`, `-1e15`, `-2^63`; `z = -3` and `z = -1` return at once), the second point at `y = 1e150` returns in 0.1 s, `1e154` in 6 s, and `1e155`, `1e200`, `1e300` give no result in 15 s: the overflow onset of the original record. A trimming circle of radius or centre coordinate `1e300` on the lifted net returns at once (0.03 s); `SmApiTrimProjectParallel` on the same huge net with a projected line returns at once too.
- **Confirmed:** yes (no result in 40 s for the nightly input, reproduced alone; gdb backtrace).
- **Rust port:** the `primitive.api_trim_ops` FFI (`run`, `validate`) refuses a trim-with-3D-curves surface (net or corner points) with a coordinate above `MAX_TRIM_SURFACE_COORD = 1e150`, the bound of the other HANG-29 guards; the runner's Rust side refuses the same input (`ffi::validate`). The Rust port returns on this input (main's runner, Rust side alone: status 0, a one-face B-rep whose record holds `inf` values, in about 1 s); an FFI-refused case is `rejected` on the C++ side, so the gate and the fuzz driver never run the Rust side on it.
