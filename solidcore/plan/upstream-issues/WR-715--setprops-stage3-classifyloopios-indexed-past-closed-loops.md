#### WR-715. `SetProps_Stage3` sizes the loop classification records to the closed loops but `ClassifyLoops` indexes them by the face's loop list: past the size it reads `SmTArray`'s zeroed slack
- **Severity:** Wrong result
- **Area:** Topology
- **Location:** `source/SMLib/src/SmFaceProps.cpp`, `SmFaceProps::SetProps_Stage3`: it collects only the face's closed loops into `sClosedLoops` and passes them, with a fresh `sClassifyLoopIOs` (`:1362`), to `SmFace::ClassifyLoops` (`source/SMLib/src/SmFace.cpp`, def. `:4218`). That function sizes `rClassifyLoopIOs.SetSize(rLoops.GetSize())` (`:4267`). It then indexes it as `rClassifyLoopIOs[lLoopIndx]` with the `m_lLoopIndx` of the seam touch lists, which `SetProps_Stage2`'s `HasSeamProblem` built against all of the face's loops. This happens in the start-touch search, in the walk's entering/pairing/exiting tests, and in the containment and orientation writes. `SmTArray::operator[]` (`source/SMLib/inc/SmTArray.h:454`) checks the bound only under `SM_DEBUG_CODE`.
- **What happens:** on a periodic face missing its seam that has a loop which is not closed, the seam touch lists count that loop and the closed loops do not. So a crossed loop's touch index can be at or past the number of records. `SmTArray::SetSize` (`SmTArray.h:499`) allocates at least `MIN_ARRAY_SIZE` (16, `:480`) records with `smos_Calloc`. So the read and the writes land in zeroed records past `m_lSize`, inside the same block:
  - `m_bArea_Loop` reads `FALSE`, so the loop counts as a no-area loop;
  - the orientation and containment written for it go into that slot, and nothing that iterates `GetSize()` sees them.

  The walk's pairing and the loop tree therefore rest on a zeroed record, not on the record of the loop that was crossed. Past the allocation (16 or more loops in that layout), it is an out-of-bounds read and write.
- **Trigger:** two STEP corpus bodies in the plain stitch-and-heal recipe (`ap203/chair.stp` body 21, `ap203/4pinplug.stp` body 1): faces whose seam touch list holds loop index 1 while one loop is classified.
- **How found:** the plain-corpus heal sweep 54k5 showed 49 of 51 HEAL-DIFF bodies first diverging at `Fix_SplitFaceAtSeams`. The port's checked indexing refused the read, so its `SetProps_Stage3` moved those faces to the not-yet list, and they never got their seams. Probes on both kernels found it: batches 54k76, 54l2 and 54l3, with the C++ under gdb, showed `ClassifyLoops` returning `SM_SUCCESS` with `SM_HNF_NO_PROBS` and no `MoveToNotYetProblems` in the C++. The Rust probes showed the touch list (loop 0, then loop 1) against one record.
- **Confirmed:** yes, on the pinned C++ (gdb, batches 54k76 and 54l2), in the reference build (`-DNDEBUG`, no `SM_DEBUG_CODE`).
- **Rust port:** the default path reproduces it. `ClassifyLoopsOut::classify_loop_io_slack` holds the zeroed records `SetSize` allocates past the size, and `ClassifyLoops` and `SetProps_Stage3` read and write them as upstream does. Past the allocation, the port returns an error instead. There is no opt-in for indexing by the target loops.
