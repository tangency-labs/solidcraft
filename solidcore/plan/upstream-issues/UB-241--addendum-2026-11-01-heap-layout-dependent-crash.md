Updates: UB-241

#### UB-241 (update, 2026-11-01). Whether the #2174 cap's outward thicken crashes depends on the heap layout
- **Location:** as UB-241 (`source/SMLib/src/SmProtoTopology.cpp`, `SmProtoTopologyManager::GlueCoincidentBrepVertices`; the faulting read in `sm_RmFromSpatialTree` via `SmBrep::GlueVertices`).
- **What happens:** the defect is the same: a read of a vertex the loop has already deleted. A use-after-free read only faults when the freed memory has been unmapped or reused in a way that leaves a bad pointer, so on the same input the C++ side sometimes crashes and sometimes finishes. Difftest case `issue2174_cap_two_rim_edges_api_shell_out` (added in tangency-labs/solidcore#2196) runs its C++ side in a forked child through the UB-241 crash trap (`eval_in_child`). It is therefore `rejected` in a run where the child crashes and `pass` in one where it finishes. The ratchet reads `pass` in the base report followed by `rejected` as a regression.
- **Trigger:** as the 2026-11-01 reproduction addendum (`SmApiShellBrepFull`, the r 10 sphere's cap above z = 5 thickened +1 with merged results).
- **How found:** two CI runs of fixture-only PRs, both based on `main` at `e967f9d40`. Neither touches the unit. In tangency-labs/solidcore#2217's `difftest-compare` the case passed. In tangency-labs/solidcore#2218's ([run 41307387451](https://github.com/tangency-labs/solidcore/actions/runs/41307387451/job/124852938151)) it was rejected: `GATE-FAIL (ratchet) case issue2174_cap_two_rim_edges_api_shell_out passed in the baseline, now rejected` (tangency-labs/solidcore#2224). The Rust side is deterministic. `crates/solidcore/tests/issue_2174_cap_outward_ub_241.rs` pins its result.
- **Confirmed:** yes, on the C++ build in CI: the two runs above, same input and same base, one crash and one result. The case is parked with `cpp_defect = "UB-241"` (`crates/difftest/known_mismatches/offset.offset_executive_p2.toml`), as UB-280's heap-layout-dependent case is.
