Updates: WR-63

#### WR-63 (update, 2026-11-17). `cone_create_canonical_preserves_inside_out_and_checks_height` is removed

The flag is gone (tangency-labs/solidcraft#14246). Its two halves are settled differently:

- **The inside-out half is the only behaviour.** `Cone::create_canonical_with_semi_angle` with `Some(height)` always passes `(inside_out, false)` as the bounded constructor's `(bInsideOut, bMakeNurbGenCurve)`, as the bounded two-radius overload does. Upstream's `(FALSE, bInsideOut)` drops an inside-out request, which is the defect this record reports.
- **The height half is withdrawn: a height not above 0 is not refused.** `Cone::create_canonical` with `height <= 0` keeps building upstream's infinite cone with `top_radius` as its semi-angle in degrees. This is a documented form, not a misuse of the argument. `SmCone.h` documents `dHeight` as "0 = make infinite cone", the definition's NOTES say "If dHeight is not specified ( <= 0 ), creates an infinitely long cylinder" (`SmCone.cpp:373`; "cylinder" is upstream's documentation slip for a cone: the code builds `SmCone(.., dTopRadius as dSemiAngleDeg, ..)`, and the semi-angle overload's NOTES make the same slip, "Returns an infinitely long cylinder", at `SmCone.cpp:306`), and the call at `SmCone.cpp:392-400` documents the argument it passes as "Angle from cone ZAxis to Cone Surface (degrees [0,90])". The radii cannot supply that angle. A cone of revolution of semi-angle `a < 90` has radius `r(z) = r0 + z tan(a)`, a function of the height, so two coaxial circles at one height lie on no such cone when their radii differ, and on every one when they agree. With the flag on, its refusal (`InvalidInput`, 1007) turned 361 goldens rows that build on main into failures (#18066's attribution).
- **Removed:** the field `UpstreamFixes::cone_create_canonical_preserves_inside_out_and_checks_height`, SolidCraft's preset line, and its entries in `fixes.json` and `issue_2260`'s list.
- **Tests:** in `surface::cone::p1`, `wr63_semi_angle_with_height_keeps_inside_out` is the record's trigger (`CreateCanonical(O, 1, 30, &h, cone, FALSE, TRUE)` is inside-out by construction: its canonical data, placement and +Z axis, base radius, positive semi-angle, `swap_uv` and `inside_out`, and its heights are asserted exactly equal to the two-radius overload's inside-out frustum, and exactly equal to the outward cone's except for `inside_out`, which reverses the normal; the opposite normal is also spot-checked at the domain midpoint). `wr63_two_radii_non_positive_height_builds_the_infinite_cone` checks the infinite cone for heights `0`, `-0`, `-5` and `-1` by asserting its canonical data exactly equal to the semi-angle overload's infinite cone with semi-angle `top_radius`; for a positive semi-angle it also spot-checks three points against the closed form. `wr63_semi_angle_and_two_radii_overloads_agree` covers the bounded overloads.
- **Results:** 58 goldens rows move: `surface.cone_p1` 28, `surface.cone_p2` 2 and `surface.surface_p2` 28 (the `common_cone_*` copies of `cone_p1`'s cases). Every one is a cone asked for with a semi-angle, a height and `inside_out`, and every one still succeeds. `crates/goldens/tests/wr63_semi_height_inside_out_moves.rs` replays each row. The new row is exactly the case built through the two-radius overload's inside-out frustum, and the old row agrees, under the goldens' rule (1e-9 relative), with the case built as upstream did (`new_bounded(.., inside_out = false, make_nurb_gen_curve = true)` on the same `Axis2Placement` frame; re-making a placement is not bit-idempotent, hence the rule rather than bit equality). No other case that asks for an inside-out cone this way moved.
