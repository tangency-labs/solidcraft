#### ND-261. `SmApiShellBrepFull` of a rounded box succeeds or fails, and places its vertices, according to heap layout
- **Severity:** Nondeterminism (in most layouts also a refusal: the shell of a valid body returns `SM_ERR` (1001) and no result; no bad body is returned)
- **Area:** Offset
- **Location:** `source/SMLib/src/SmOffsetExecutive.cpp`, `SmOffsetExecutive::DoExtendedOffset` → `PiecewiseMerge` → `SmMerge::PiecewiseMerge`, whose state is held in relations and maps keyed by object address (`SmMapPtrToPtrs`, `std::unordered_map`, `source/SMLib/inc/SmMapPtrToPtr.h:115`; the general hazard is ND-2). Traced under gdb in a failing layout (release build): `SmMerge::PiecewiseMerge` runs one `SM_BO_PARTIAL_MERGE` and one `SM_BO_MERGE` `ManifoldBoolean` per offset surface. The first 15 return `SM_SUCCESS`; the 16th (the `SM_BO_MERGE` of the eighth surface) fails in `SmMerge::MakeFaceuse` (`SER(SM_ERR)` at `SmMerge.cpp:7071`: the other edge's start vertex is mated to a B-rep vertex that is neither end of the mated B-rep edge). A succeeding layout runs the same sequence, and that call returns `SM_SUCCESS`. Which address-ordered state decides the outcome is not localised in the C++.
- **What happens:** the same call on the same inputs, in the same binary, gives different results depending only on allocations made before it.
  - A 30 x 20 x 10 box with all twelve edges rounded r3 (`SmApiFilletEdges`, circular, G1), shelled 2 inward with extended convex edges and merged results, fails in most layouts and builds a body in others:
    - shelled closed, it returns `SM_SUCCESS` with a body in some layouts and `SM_ERR` with none in most;
    - open at the top, the same.
  - The same box with four vertical edges (or one) rounded shells successfully in every layout, but the result's vertex positions and tolerances are permuted between vertices from layout to layout. The same values appear on different vertices (e.g. 17.99999974766135 and 17.99999949532269, 2.0294561340652423e-5 and 2.029456140616126e-5), the signature of tolerance merges by midpoint averaging applied in a different order. The mass properties then differ at about 1e-9 relative.
  - With only one vertical edge, the four vertical edges or the four top edges rounded, the closed shell is a manifold solid, so the failure needs the corner blend patches where three rounds meet.
  - Some layouts crash (UB-264).
- **Trigger:** `SmApiCreateBox(0, 30, 20, 10)`; `SmApiFilletEdges` (r3, cross section 1, continuity 1, thumbweight 1) on all twelve edges, on the four vertical edges, or on one vertical edge; then `SmApiShellBrepFull(-2, TRUE, TRUE, FALSE, open)`, with `open` empty or the plane face at z = 10.
- **How found:** SolidCraft regression rig on the SMLib fork (tangency-labs/solidcore#460, which reported the open shell as invalid there). Then:
  - a C++/Rust comparison case of `blend.fillet_executive_p3` whose C++ status changed (1001 → 0) between two builds whose only change came after the shell call;
  - a heap-layout sweep: an `LD_PRELOAD` constructor allocates 2N chunks of S bytes before `main` and frees every other one (S in 16, 48, 80, 128, 256, 512; N in 2, 16, 64, 128), as for ND-259.
- **Confirmed:** yes, on the C++ reference (prebuilt c9c5979 release build, x86-64 Linux), cases `real-box-fillet12-r3-shell-closed-issue-460`, `real-box-fillet12-r3-shell-open-top-issue-460`, `real-box-fillet4v-r3-shell-closed` and `real-box-fillet1v-r3-shell-closed` of `blend.fillet_executive_p3`, one process per layout, 25 layouts (no preload plus 24). 19 processes completed and 6 crashed (UB-264).
  - Closed twelve-edge shell: `SM_SUCCESS` in 1 of 19 layouts, `SM_ERR` in 18.
  - Open-top twelve-edge shell: `SM_SUCCESS` in 6 of 19, `SM_ERR` in 13.
  - Four-edge and one-edge controls: vertex positions and tolerances permuted in all 19, with a layout-dependent number of differing values (4 edges: 21 to 32; 1 edge: 1 to 9) against the port's deterministic order.
  - Read back under gdb (gdb shifts the layouts), a successful closed shell is a valid closed manifold solid: 48 vertices, 96 edges, 52 faces, `SmApiBrepIsManifoldSolid` TRUE, volume 3116.5132. The exact volume of the rounded box less its rounded inner offset is 3116.484, a 9.4e-6 relative difference; the same mass call on the one-edge control is 2.8e-6 from its closed form.
  - A successful open-top shell reports `SmApiBrepIsManifoldSolid` FALSE (mass status 1007). Its topology also differs between layouts: 19 vertices, 43 edges and 24 faces in two layouts; 19, 45 and 24 in a third.
- **Fix:** iterate the relations in a deterministic order (insertion order, or sorted by a stable object id) wherever the order reaches topology or geometry (as ND-2, ND-259).
- **Fixed upstream:** in usd-brep v1.0.1 (3fd5b95), for the twelve-edge shells.
  - In the same 25-layout sweep against the 1.0.1 reference, both shells return `SM_SUCCESS` in every layout, and no layout crashes.
  - The reference pin moved to 1.0.1, and the port follows it. In the pin101 gate run (C++ reference and port both at 1.0.1), `issue_460_closed_shell` passes (manifold solid, volume within 1e-5 of 3116.484). `blend.fillet_executive_p3 --filter shell` passes 11 of 11 cases with max_rel_err 0, including both twelve-edge shells and the two controls.
  - The controls' vertex order was compared only in the run's default layout, where it agrees with the port. Whether it still varies with heap layout in 1.0.1 has not been re-swept; the ND-2 hazard is unchanged there.
- **Rust port:** `geom::tol::Relation` iterates in sorted handle order, so the port is deterministic.
  - At c9c5979 it refused both twelve-edge shells in every run, while the C++ built a valid closed shell in some layouts, so there the port was worse than C++.
  - The port failed in the same function as the C++: `MakeFaceuse`'s edge-orientation lookup (`boolean::merge::p2::orientation_to_find`) in one pairwise merge of the offset's `PiecewiseMerge`.
  - Traced with gdb, that merge's `SetRelationships` mated the intersection edge's start vertex to B-rep vertex 8, while the imprinted B-rep edge runs from vertex 14 to 15. No vertex was glued, squeezed or combined in that merge, so the intersection edge definition had been trimmed to a point off its vertex definition.
  - 1.0.1's new distance check in `SmEdgeDefinition::IsInteriorPoint` addresses exactly that trimming: a closest point farther than the tolerance is not interior, so `UpdateEdges` no longer trims there. Whether that change alone is sufficient was not isolated; the port took all of 1.0.1 at once.
  - Details: `plan/findings/offset.offset_executive_p2--issue-460-corner-patch-piecewise-merge.md`.
