Updates: WR-444

#### WR-444 (update, 2026-11-16). `point_solve_keeps_triangle_guess` is removed

`SurfPtGlobalSolver::find_polygon_guess` always keeps the suspicious control-net triangle guess as a candidate. It returns that guess when it is nearer on the surface (`CalcFuncVal`) than the nearest control point's guess. The guess stays suspicious, so the grid search still runs. The fix is now unconditional and the flag is gone. SolidCraft already ran with it on. Removed: the field `UpstreamFixes::point_solve_keeps_triangle_guess`, SolidCraft's preset line, its entry in `fixes.json` and every test setting of it (#14246, group B surface-generic).

- **Results:** goldens rows of `surface.surface_point_solve_p2` (28), `surface.surface_p3`, `surface.surface_p4`, `query.api_queries`, `blend.fillet_geom_p4` and `intersect.surface_drop_lib_p2` move. The pull request's class table gives the certificate for each row.
  - In all 28 `point_solve_p2` rows (rough and polygon guesses), replaying `CalcFuncVal` at the old and new guesses gives new <= old. The new guess is strictly better wherever it moved.
  - The control-point indices are a separate output. `FindRoughGuess` returns the grid's uv when it wins but always the polygon guess's indices, which are now the triangle's. In 9 rows only these indices move (gen0318, gen0349, gen0413, rev_gen0217, `surface_sms_pt03/05/06/11/12_op0`). The indices only place `RefineGuessByGrid`'s ±1 Greville window, which runs only when the first local solve finds no answer, and which keeps its input guess unless a grid point is strictly better. No `Solve` row of `surface.surface_point_solve_p1`, `_p2` or `_p3` moves (every moved `_p2` row is a rough or polygon guess record).
  - `query.api_queries` `rational_kind9_100000_seam_hi`: the old row was the exact foot (u = 0.5, distance 1e5 from (2e5, 1e-7, 0) on the sphere r = 1e5); the new one is 1 ulp off (u = 0.49999999999999994, distance 1 ulp below 1e5). This is accepted because 1 ulp of u is the rounding floor of the solve there: the Newton step's numerator `(S - P) . S_u` carries an evaluation error of order eps |S - P| |S_u| (|S - P| = 1e5, |S_u| about 2.8e5), so the step has an error of order eps R / (2 |S_u|), about 4e-17 per unit of the error constant, against an ulp of 5.6e-17 just below 0.5. Neither start can resolve u closer than that; the old run happened to stop on 0.5 exactly. Snapping to the seam would be a special case, not a root fix, so none is made.
  - Three rows move downstream of a point solve, each checked with exact rational evaluation of the surface: `surface.surface_p3` gen2086 covers a surface with an identical copy of itself (the true distance is 0; `max_dist` goes 2.4e-12 -> 4.1e-12 against a tolerance of 1e-7, success and domain unchanged); `blend.fillet_geom_p4` gen0004's moved pcurve start maps to within 6.5e-16 of its vertex (old 1.1e-15; tolerance 1e-10); `intersect.surface_drop_lib_p2` gen0345's end point is now the nearest point of the domain's v-min edge to the curve point (0.72679 against the old corner's 0.74943; the old corner was not a constrained minimum).
- **Tests:** `surface::surface_point_solve::p2::tests::a_point_solve_finds_the_point_on_stacked_runs` (was `..._with_the_fix`) runs on a default kernel.
