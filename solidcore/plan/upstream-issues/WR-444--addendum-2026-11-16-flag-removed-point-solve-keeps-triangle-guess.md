Updates: WR-444

#### WR-444 (update, 2026-11-16). `point_solve_keeps_triangle_guess` is removed

`SurfPtGlobalSolver::find_polygon_guess` always keeps the suspicious control-net triangle guess as a candidate. It returns that guess when it is nearer on the surface (`CalcFuncVal`) than the nearest control point's guess. The guess stays suspicious, so the grid search still runs. The fix is now unconditional and the flag is gone. SolidCraft already ran with it on. Removed: the field `UpstreamFixes::point_solve_keeps_triangle_guess`, SolidCraft's preset line, its entry in `fixes.json` and every test setting of it (#14246, group B surface-generic).

- **Results:** goldens rows of `surface.surface_point_solve_p2` (28), `surface.surface_p3`, `surface.surface_p4`, `query.api_queries`, `blend.fillet_geom_p4` and `intersect.surface_drop_lib_p2` move. The pull request's class table gives the certificate for each row.
  - In all 28 `point_solve_p2` rows (rough and polygon guesses), replaying `CalcFuncVal` at the old and new guesses gives new <= old. The new guess is strictly better wherever it moved.
  - The control-point indices are a separate output. `FindRoughGuess` returns the grid's uv when it wins but always the polygon guess's indices, which are now the triangle's. In 9 rows only these indices move (gen0318, gen0349, gen0413, rev_gen0217, `surface_sms_pt03/05/06/11/12_op0`). The indices only place `RefineGuessByGrid`'s ±1 Greville window, which runs only when the first local solve finds no answer, and which keeps its input guess unless a grid point is strictly better. No bound ranks the old and new indices: the window is a retry heuristic, and where it sits has no monotone effect on the outcome. Acceptance is unchanged, because the window only seeds a retry. No `Solve` row of `surface.surface_point_solve_p1`, `_p2` or `_p3` moves (every moved `_p2` row is a rough or polygon guess record).
  - `query.api_queries` `rational_kind9_100000_seam_hi`: the point is (2e5, 1e-7, 0) and the surface is the sphere of radius 1e5. Neither row is the exact foot. The old row has u = 0.5 and y = 5.000000000000517e-8, not 5e-8: the net's weights are the rounded sqrt(0.5), so the stored surface is not exactly a sphere. The new row has u = 0.49999999999999994, the next double below. On the stored surface, exact rational evaluation of the Newton numerator f = (S - P) . S_u gives +9.31e-7 at u = 0.5 (left piece) and -7.95e-6 at the new u, so its root lies strictly between the two doubles. A rounding enclosure, counted op by op over the stepper's own evaluation order with one (1 + d), |d| <= 2^-53, per operation, bounds the evaluation error of f by 6.9e-4 at both u (7.5e-4 at u = 0.5 from the right). The exact f lies inside that enclosure at both u, so the evaluated numerator cannot tell either u from a root, or the two apart. Snapping to the seam would be a special case, not a root fix, so none is made.
  - Three rows move downstream of a point solve. `surface.surface_p3` gen2086 covers a surface with an identical copy of itself, so the true distance is 0. `max_dist` goes 2.4e-12 -> 4.1e-12, and both are at most the tolerance 1e-7 by construction: every sample that enters `max_dist` is followed by a failure return when it exceeds the tolerance the point solve runs with, and both runs succeed (success and domain unchanged). S_u| / |S_u| = 2.6e-17, not 0), nearer the curve point than the old corner (0.72679 against 0.74943). The old corner was not a constrained minimum.
