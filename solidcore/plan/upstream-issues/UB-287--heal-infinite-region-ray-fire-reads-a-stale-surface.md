#### UB-287. `HealBrep`'s infinite-region ray fire reads a surface whose memory no longer holds a surface
- **Severity:** Crash / undefined behaviour
- **Area:** Healing
- **Location:** `SmSurface::GetFace` (`source/SMLib/src/SmSurface.cpp:11987`), called by `SmTLSPointFace::SolveIt` (`source/SMLib/src/SmTopologySolver.cpp:661`; `pSurface->GetFace()` at `:701-702`, on the surface taken from the solver's tree object). The fault is at `GetFace` + 14, the virtual `IsKindOf` call on `m_pOwner`. The `m_pOwner` read from the surface (offset 0x20) is `0x3fdd16872b020c4a`, the bit pattern of a double near 0.45, not a pointer.
- **Signal:** SIGSEGV, `si_code` 128 (`SI_KERNEL`): a general-protection fault on a non-canonical address, the "pointer" above. The `SmSurface *` the solver holds points at memory that is no longer that surface: freed and reused, or never a surface. Which object it was and when it was freed have not been traced.
- **Call path:** `SmSurface::GetFace` <- `SmTLSPointFace::SolveIt` <- `SmTopologySolver::LocalSolve` <- `SmGlobalSolver::SolveBranch` (2 levels) <- `SmTopologySolver::SolveTrees` <- `SmTopologySolver::BrepPointSolve` <- `SmBrep::RayFire` <- `SmBrep::FindInfiniteRegion` <- `SmBrep::FindAndSetInfiniteRegion` <- `SmHealData::Fix_InfiniteRegion` <- `SmHealData::HealTgts` <- `SmHealData::HealBrep` <- `SmBrep::HealBrep`. This is the same ray fire as UB-67's 2026-10-31 update, but a different fault: there a NULL surface in `BuildPolarBox`, here a surface pointer to reused memory.
- **Trigger:** STEP Tools corpus `ap203/jack_in_the_box.stp`, body 29, through the difftest STEP corpus path (`difftest --step-case`: `CreateFacesWithCurves` per face, `SmApiStitchIntoSolid`, counts, manifold, area, volume, then `SmApiHealBrep`). The body has 26 faces, 60 edges and 36 vertices, and stitches into a manifold solid (2 regions, 2 shells). The crash is in the heal.
  - It depends on memory layout. Under `--step-case` it crashed in all three runs (two of main, one patched build) and under gdb with address randomization off.
  - Under `--step-corpus`, where earlier bodies of the file have been built in the same process first, it did not crash, and the healed volume came out as 28.21.
- **How found:** the C++ child of a STEP corpus run exited with SIGSEGV (rc 139; batch 54g9f3a577). It was rerun alone under gdb, launched by gdb, on the clean main build (batch 54g9f3b2). The prebuilt reference libraries have no line info, so frames are function + offset, and the field and value are read from the disassembly and registers.
- **Confirmed:** yes, the crash on this path, reproduced alone. That the object's memory holds a non-pointer is read from the faulting register. That it is a use after free is suspected, not traced.
- **Rust port:** no crash. Arena ids replace the surface pointers, so a deleted face's surface cannot be reached through a stale handle. The Rust side builds, stitches and heals the body in every run, with the same counts after the heal and a manifold result.
