Updates: WR-164

#### WR-164 (update, 2026-10-31). The extended-surface `SwapUV` double negation has an opt-in single negation

- **Severity:** Wrong result
- **Area:** Surfaces and volumes
- **Location:** `source/SMLib/src/SmOffsetSurface.cpp:1767` and `:1772`, `SmOffsetSurface::SwapUV`.
- **What happens:** upstream negates the distance once after swapping the extended surface and again after swapping the base. With a stored extension the two negations cancel: an owning offset keeps its distance and ends up on the other side of its base, so `Offset(uv)` after the swap is not the pre-swap `Offset(vu)`. An offset without an extension negates once, as it should.
- **Trigger:** `SwapUV` on an owning offset that has stored an extension (fixture `extension_sequence` and `extension_sequence_negative`).
- **How found:** read during porting; fixture `extension_sequence` confirmed it against the pinned C++.
- **Confirmed:** yes (fixture `extension_sequence`).
- **Fix (port, opt-in):** `Kernel::fixes.offset_swap_uv_extended_distance` (off by default: pinned C++ parity). When it is set and the extended surface was successfully swapped, the base's successful swap no longer negates the distance a second time, so the extension's one negation remains and `Offset(uv)` after the swap equals the pre-swap `Offset(vu)`. The gate is only on the second negation after a successful base swap: a failed extension swap, a failed base swap and a non-owned base keep their upstream order and partial state (extension swapped and negated before `SM_ERR`), and an offset with no extension still negates once. Nothing else in `SwapUV` changes.
- **Test:** `surface::offset_surface::tests::wr_164_swap_uv_with_an_extension_negates_once` builds the fixture's real B-spline base through the public `BSplineSurface::from_data` (degree 3 x 3, 5 x 5 non-rational net, knots `[0,0,0,0,.5,1,1,1,1]`), makes a stored extension with the public out-of-domain evaluations `(1.4,0.5)`, `(2.6,0.5)`, `(1.2,0.3)`, and checks both distances `0.4` and `-0.3`: the default swap keeps the distance and does not map `uv` to `vu`; with the flag the distance is negated once and public `evaluate_point` values satisfy `O_after(u,v) = O_before(v,u)` to pure relative `1e-9` at three asymmetric inside-domain parameters, and a second swap restores the distance and the evaluations. Controls: an owned offset with no extension negates once with the flag on or off; a non-owned offset keeps the extension's negation and `SM_ERR`; a failing base edit notification keeps the notification order, the propagated error, the one negation, the stored extension and an unchanged base point. The non-owned and failing-notification controls were recorded with the flag off only; their tests now loop both flag states, but that ON loop is not executed in the bounded test-only follow-up (the parent runs the final offset module). These measure the distance, extension presence, public point values, error operation and notification order, not the whole edit end to end. The existing fixture parity is not a new C++ measurement.
