Updates: WR-90

#### WR-90 (update, 2026-10-31). Opt-in longest-gap index update on `GapArray::append`

- **Status in the port:** `Kernel::fixes.gap_array_append_updates_longest`, off by default. The default retains the pinned C++ behavior, where `GapArray::append` copies gap records into the receiving array without updating the index of the longest gap (`m_lMaxGap3d`).
- **Location:** `source/SMLib/inc/SmGap.h:882-892` (`SmGapArray::Append`) at v1.0.1 (`3fd5b95`); `crates/solidcore/src/heal/gap.rs`, `GapArray::append`, `GapArray::append_opt_in`, and `GapArray::append_with_kernel`.
- **What changes:** `GapArray::append` defaults to preserving pinned C++ behavior (`append_opt_in(&other, false)`). When `gap_array_append_updates_longest` is enabled (via `append_opt_in(&other, true)` or `append_with_kernel(&other, kernel)`), if `other` has a longest gap (`other.max_gap_3d = Some(other_idx)`), its length is compared against the receiving array's current max gap. If `other`'s gap is strictly longer than the receiving array's max gap, or if the receiving array previously had no max gap (such as an empty array), the receiving array's `max_gap_3d` is updated to `Some(old_len + other_idx)`. If `other`'s gap is smaller or equal, or if `other` has no max gap, the existing `max_gap_3d` is preserved.
- **Why it matters:** upstream `SmGapArray::Append` adds elements from another array to its internal collection but never updates `m_lMaxGap3d`. Consequently, calling `GetMaxGap()` or `GetMaxGapLength()` after appending longer gaps returns an outdated smaller gap (or null / length 0 if appending into an empty array). When healing workflows or edge/vertex gap aggregations concatenate gap arrays, the true maximum gap across the combined segments was lost or misreported.
- **Regression evidence:** `wr90_gap_array_append_default_retains_upstream_unupdated_index` verifies that under default settings, appending larger gaps preserves the unupdated index `Some(0)` (retaining length 0.5 when gaps up to 3.0 are appended) and appending to an empty array retains `None` and 0.0 length. `wr90_gap_array_append_opt_in_updates_longest_gap` verifies that when opt-in is enabled (both via explicit boolean and via `Kernel::fixes.gap_array_append_updates_longest`), `max_gap_index()` is properly updated to `Some(2)` and `max_gap_length()` reports 3.0. `wr90_gap_array_append_to_empty_array` confirms appending to an empty array sets the max index and length. `wr90_gap_array_append_smaller_or_equal_retains_existing_max` confirms appending strictly smaller or equal gaps retains the existing maximum gap. `wr90_gap_array_append_empty_array` confirms appending an empty array leaves existing state intact.
- **Native evidence:** `heal.gap` passes all targeted unit tests and difftests (`cargo run --profile difftest -p difftest --features cpp -- --unit heal.gap`) with zero regressions and bit-for-bit parity under default behavior.
- **Scope:** WR-90 only. WR-88 (surface V sample stride) and WR-89 (trimmed knot spans) remain independent.
- **Tracking:** tangency-labs/solidcore#2072. WR-90 is a file record; GitHub issue #90 is unrelated.
