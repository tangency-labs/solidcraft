#### ND-258 (update, 2026-10-27). The heap order also picks which coincident plane survives, so geometry and later topology vary too
- **Severity:** Nondeterminism
- **Area:** Topology
- **Location:** as ND-258: `source/SMLib/src/SmMerge.cpp:2718` (`SmMerge::ManifoldBoolean` STEP 1 fills `m_sIntersectionEdges` from `SmTopologyIntersector::GetMappedBrepObjects`, `SmTopologyIntersector.cpp:945`, which walks the pointer-keyed `std::unordered_map` `m_pOToB`, `SmMapPtrToPtr.h:42`/`:219`; upstream marks it `#ifdef SM_DEFINED_HASH_ORDER static_assert(false, "not implemented")`). Newly reached: `SmMerge::BooleanPostProcess` (`SmMerge.cpp:848`, `:884`) calls `SmEdge::IsTopological` (`SmEdge.cpp:4986`; `paSurf[0]` is the first face's surface, `:5016`), which calls `SmSurface::CoverOtherCoincidentSurface` (`SmSurface.cpp:8327`). There, for two planes the first surface covers the second and wins (`:8397`). `DeleteEdge` (`SmMerge.cpp:1140`) then keeps that surface.
- **What happens:** ND-258 says the topology and geometry are the same up to where each loop's cycle begins. That is not so when the two operands have coincident faces. The first coincident edge in heap order decides whose `SmPlane` absorbs the other, so the merged face keeps one operand's plane or the other's. The 3D face is the same, but its parametrisation (plane origin, so its UV domain) differs. Operations that build on that face then diverge further: fillets of single edges of the union give different result topology for some edges (below).
- **Trigger:** `SmApiBooleanUnion` of `SmApiCreateBox` A (origin (-1,0,0), size (20,10,10)) and B (origin (-1,2,5), size (10,10,10)): their x = -1 faces are coplanar and overlap. The merged x = -1 face's domain is (-0.75,-0.75)-(15.75,12.75) with A's plane and (-5.75,-2.75)-(10.75,10.75) with B's (shifted by B - A in (z, y) = (5, 2)). Found as `blend.fillet_executive_p3` fuzz case `fuzz00712` (a mutation of `stubs3-union-inset-side-step-edges13-17-r1`: both origins x = -1, edges [13], r = 1). Details, the per-edge table and the reproduction: `plan/findings/blend.fillet_executive_p3--fuzz00712-box-union-coplanar-heap-order.md`.
- **How found:** `difftest --fuzz 1000` on `blend.fillet_executive_p3` (PR #1298's gate) reported one `differs`. Reruns showed the C++ value, not the Rust, changing with case order and with unrelated binary changes.
- **Confirmed:** yes. In a temporary harness build, the forked C++ child allocated N dummy blocks (24 to 264 bytes) before the call and freed them after it, which changes only heap addresses. For edge 13: N = 0 and 8 give A's plane (as the Rust); N = 1, 2, 3, 5, 13, 21, 34, 55, 89 and 144 give B's. The Rust result was A's plane at every N. Edge 0 shows at least three C++ outcomes across N (Rust's at N = 4). The site chain above is from reading the source at 3fd5b95 (v1.0.1). No debugger trace of the edge order was taken for this trigger (ND-258's gdb trace shows the STEP 1 order varying).
- **Rust port:** unchanged and deterministic. `boolean::topology_intersector::p1` keeps the mate maps as `BTreeMap`s over arena handles (`mapped_primary`), so the intersection edges come in the other B-rep's edge-id order, and `topology::edge::is_topological` / `cover_other_coincident_surface` keep upstream's "first face's surface wins" rule. The port therefore matches one of the C++ outcomes, not all of them. ND-258's loop-start canonicalisation in the `boolean.merge_p4` runner does not cover this. A surviving-plane difference is a different surface, so a runner cannot canonicalise it without dropping the comparison.
