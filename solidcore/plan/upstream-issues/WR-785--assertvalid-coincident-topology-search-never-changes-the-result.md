#### WR-785. `SmBrep::AssertValid` runs the coincident-topology search and never uses its result: `ContainsCoincidentTopology` returns TRUE unconditionally, `AssertValid` consumes it inverted, and its report is commented out

- **Severity:** Wrong result
- **Area:** B-rep validation (`AssertValid`)
- **Location:** `source/SMLib/src/SmBrep.cpp:30435`, `SmBrep::ContainsCoincidentTopology` (def. `:30407`); `:35373` and `:35374`, `SmBrep::AssertValid`.
- **What happens:** three coupled defects make the check a no-op, while its search over every pair of vertices, edges and faces still runs on every `AssertValid`.
  1. `ContainsCoincidentTopology` initialises its accumulator `SmBoolean bCheck = FALSE` (`:30435`). The comment above the return says `bCheck` means "all checks passed": it should start `TRUE` and become `FALSE` when an `SM_ASSERT_PAIR_REPORT(..., SM_LEVEL_2, ...)` fails. It starts `FALSE`, so `bCheck &= ...` stays `FALSE`, and `return !bCheck` (`:30842`) is `TRUE` whatever the search found.
  2. `AssertValid` folds that boolean into its result as it is: `bRtn &= this->ContainsCoincidentTopology(-1,NULL,NULL,pAList)` (`:35373`). With 1 it is always `TRUE`, so it never changes `bRtn`. Read as "coincidence found", it would need `bRtn &= !...`.
  3. The intended report, `SM_ASSERT_BOOLEAN_REPORT(15, SM_LEVEL_2, (this->ContainsCoincidentTopology(...)==FALSE), ...)`, is commented out (`:35374`). `AssertValid` calls the search at the default level `SM_LEVEL_0` with `NULL` pair outputs, so the search adds no report and returns no pairs.
- **Trigger:** every `AssertValid`. A body with coincident vertices, edges or faces passes it. The only other caller is `SmBrep::DrawCoincidences` (`:34671`), a debug drawing of the pairs.
- **How found:** reading the C++ while profiling a SolidCraft design (a knurled grip) whose rebuild spent most of its time in the per-feature `AssertValid`, much of it in the search.
- **Confirmed:** yes, in the Rust port, which matched the C++ line for line: `contains_coincident_topology` set `found` to `true` and never changed it, `assert_valid/brep.rs` did `rtn &= ...found`, and at level 0 its pair reports always passed.
- **Fix:** none that makes the search a validity test. Making it fire (start `bCheck` `TRUE`, consume it negated, restore the test-15 report) fails bodies that are valid: a hole tangent to a face or two holes touching at a point leave a pinch, kept as coincident edges or vertices, and a sweep's stitch glues coincident lamina edges. Upstream's commented-out report is consistent with that. `AssertValid` should not run the search.
- **Rust port:** not ported. `AssertValid` does not run the search (`topology/brep/validation/assert_valid/brep.rs`, its header's Deviations), and the search and its span-box pruning are removed. A face's own coincident vertices and edges remain its `SmFace` tests 32, 33 and 34.
- **Results that change:** no check's result or report. The search did edit the body it checked: its edge/face queries built the faces' trim caches with tolerance adjustment (new UV trim curves, moved control points, a raised vertex tolerance), and an operation's result check and SolidCraft's per-feature check left those edits in the body. Without the search a body keeps what its operation built. The shell of `issue_1795_shell_hole_through_arc::shell_open_at_the_top_is_valid_on_the_default_split_path` changes volume by 1.5e-8 relative; every golden outside the search's own unit, and both kernel rigs, are unchanged. An error the search raised (an unported or cancelled solve) no longer reaches `AssertValid`.
