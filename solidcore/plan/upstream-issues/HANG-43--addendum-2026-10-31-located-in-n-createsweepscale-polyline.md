#### HANG-43 (update, 2026-10-31). Located: the path polyline of `N_CreateSweepScale` (HANG-5); the `sweep.api_brep` FFI refuses huge curved curve-sweep paths
- **New trigger (nightly fuzz run 41040730716, 2026-10-30, `sweep.api_brep` `fuzz00293`, `cpp: no result after 20 s`):** `SmApiCreateCurveSweepFromFaces` of one disc (radius 2.39) along a four-point `SmApiCreateCurve` path whose third point is mutated to `z = 1e300`, with a line scale curve and a four-point scale reference, `NULL` options.
- **Location (gdb on the v1.0.1 reference, x86-64, two samples):** `SmApiCreateCurveSweepFromFaces` -> `SmPrimitiveCreation::CreateCurveSweepFromFaces` -> `CreateCurveSweep` -> `SmBSplineSurface::CreateSweepSurface` -> `N_CreateSweepScale` -> `N_ApproxCrvWithPolyline` (`NL_CrvGeom.cpp:1531`, in `N_Realloc1dRealArray`). `N_CreateSweepScale` (`NL_SrfAdv.cpp:15506`) polygonizes each trajectory segment to `0.5 * E` (`E = SM_ZONE_TOL_3D = 1e-5`, passed by `SmApiCreateCurveSweepFromFaces`) and only relaxes the tolerance tenfold after a pass returns with more than 1000 points; the first pass on a path that dwarfs the tolerance does not return. This is the regime of HANG-5 ("subdivides forever below floating-point resolution"), not a new loop.
- **Regime (per-call timing, release reference, the nightly input with the spike point at `z`):** `1e10`..`1e13`: 0.02-2 s; `1e14`: 4.9 s (the Rust side then takes 5.8 s); `1e15`, `1e20`, `1e30`, `1e120`: 0.02-1.3 s; `1e40`, `1e50`, `1e60`, `1e80`, `1e140`, `1e150`, `1e154`, `1e155`, `1e200`, `1e300`, `-1e50`, `-1e300`: no result in 10-30 s. Erratic in the magnitude because the spike's chord deviation (a few units in x) is lost in the rounding of coordinates that large. The curvature regime is smooth instead: a quarter-arc path (`SmApiCreateArc`) of radius `1e4` returns in 0.04 s, `1e5` in 0.2 s, `1e6` in 2.9 s, `1e7` in 13.5 s; `1e8`, `1e9`, `1e10`, `1e11`, `5e11` and full circles of radius `1e10`, `1.5e11` give no result in 25-30 s (the polyline has about `sqrt(r / tol)` points and grows by 150 per reallocation). A line path (degree 1, not subdivided) of length `1e300` returns at once, and the same spike path translated by `1e8`..`1e40` (spike at `z = 1`) returns in 0.02-4 s.
- **Confirmed:** yes (no result in 30 s for the nightly input, reproduced alone; the corpus inputs `fuzz01218` and `fuzz01458` of this record are refused by the same guard).
- **Rust port:** the `sweep.api_brep` FFI refuses, for the curve sweeps (`CurveSweep`, `FromFaces`, `FromEdges`, `FromBoxFace` and the attributed variants), a path other than a line segment whose extent (the bounding-box diagonal of `SmApiCreateCurve` points, the diameter of an arc or circle) exceeds `MAX_PATH_EXTENT = 1e8` (`check_path_extent`); every fixture and generated path stays below about `1e7`. The runner's Rust side applies the same check, so the case is a harness error on both sides (the Rust port itself returns status 1001 on the nightly input, in under 1 s). `SmApiCreatePipeSweep` with a `1e300` path point is UB-232 (SIGFPE), not this record; the pipe and planar-path sweeps are not guarded here. Regressions: `crates/difftest/tests/fuzz_corpus/sweep.api_brep.json` (`fuzz00293_from_faces_path_1e300`; `fuzz01218_cpp_hang` and `fuzz01458_cpp_hang` now run the C++ side and expect the refusal).
