#### WR-513. `SmFilletErrorInfo::NoteError` for a vertex records nothing, so an unsupported fillet corner loses its code, vertex and comment
- **Severity:** Wrong result
- **Area:** Blend/fillets
- **Location:** `source/SMLib/src/SmFilletExecutive.cpp:131`, `SmFilletErrorInfo::NoteError(const SmVertex *, SmFilStatus, SmFilletErrorType, const TCHAR *)` (the `SM_REF3` overload), and `SmFilletExecutive::CreateFilletCorners` (`:1874`), which skips a vertex `SmFilletCorner::Create` returns null for with only `SM_DBG_WARN("Error or Unimplemented corner case")`. Pin: `3fd5b9548d19aa8c12c29bc9637a96d42a06f8a5` (v1.0.1).
- **What happens:** The vertex overload of `NoteError` reads the vertex number and stores nothing: `m_pFilletedVertex`, `m_vLocation`, `m_eErrorCode`, `m_eFilletStatus` and `m_cComment` are untouched. `CreateFilletCorners` does not note the missing corner at all, so a blend whose edges meet at a vertex no corner type handles reaches the caller with no code, vertex or comment. The edge overload (`:150`) records all of them, and `operator=` (`:62`) copies the code, status, corner/edge type, executive and vertex but not the location or comment.
- **Trigger:** A blend at a vertex where the filleted and unfilleted edges (and their convexity) match no `SmFilletCorner` type. The issue's case is a 20 cube less a radius-5 hole whose wall touches the side `y = 0` along a line, with the top rim and the side's top edge chamfered 3: the blends meet tangentially at the touching point.
- **How found:** tangency-labs/solidcore#1469; pinned source read. The fork's fix is tangency-labs/smlib@a73cf5e ("fillet: a vertex no blend corner handles keeps its error, SMLIB_ERR_CORNER_UNSUPPORTED").
- **Confirmed:** no. The pinned C++ is not run for this record; the Rust port reproduces the pinned no-op with the opt-in off and the retained note with it on (see below).
- **Fix (fork):** the vertex overload stores `m_pFilletedVertex`, `m_vLocation = pBadVert->GetPoint()`, `m_eErrorCode`, `m_eFilletStatus` and the comment (a null comment keeps the old text), and `CreateFilletCorners` notes the missing corner with the new `SM_FILERR_CORNER_UNSUPPORTED` and `"Corner case not implemented"`. The fork's `SmFilletErrorType` gains `SM_FILERR_CORNER_UNSUPPORTED` after `SM_FILERR_NOT_EXACT`, and the C API maps it to `SMLIB_ERR_CORNER_UNSUPPORTED` (-1111); the -1111 is a capi status, not an `SmFilletErrorType`.
- **Rust port:** opt-in `Kernel::fixes.fillet_vertex_error_diagnostics` (default `false`, pinned behaviour) in `crates/solidcore/src/blend/fillet_executive/p1.rs`:
  - `ErrorInfo::note_vertex_error` records the vertex, its point, the status, the code and the comment; a null vertex records nothing and a null comment keeps the old text.
  - `FilletExecutive::create_fillet_corners_recording_vertex_errors` notes `FilletErrorType::CornerUnsupported` (9; this port keeps its existing codes 0..=8, including the non-pinned `NoRoom` = 8, and defines no `SM_FILERR_NOT_EXACT`, so the fork's 10 is not used) with `SM_FIL_FAILURE` and `"Corner case not implemented"` when the owner's factory reports no corner. It keeps the pending vertex entry and the operation's result, so the note does not make the unsupported corner succeed.
  - `FilletSession::do_fillet` keeps that note in `error_info()` across the later stage's failure only while the policy is enabled: the returned error is still the later stage's own status, but the session reports the retained code 9, status 2, vertex, location and comment. A stale unsupported-corner code does not replace the current stage's diagnostic with the policy off. This is an opt-in observation only; no corner is removed and no early failure is introduced.
  - The live session's `create_corners` (`crates/solidcore/src/blend/fillet_executive/session.rs`) supplies the vertex's point and is the production caller, so the policy is consulted on the real executive path.
  - The whole-operation wrappers (`fillet_edges` and the other entry points in `api.rs`) drop their session and return only the later fillet failure, so the retained note is not in their `Result`. It is readable through the public `FilletSession::create_corners` / `FilletSession::error_info`; the default operation result is unchanged.
  - Tests: `vertex_error_note_retains_all_fields_and_keeps_a_null_comment`, `create_corners_notes_an_unsupported_vertex_only_when_opted_in`, `create_corners_original_factory_shape_still_notes_without_a_location` (`p1.rs`); `create_corners_consults_the_vertex_diagnostics_fix` and `do_fillet_keeps_the_missing_corner_note_or_the_same_later_failure` (`session.rs`, a pentagonal pyramid whose apex has five edges and three filleted).
  - No CAPI mapping is added; the Rust enum variant is the fork's `SmFilletErrorType`, not -1111.
  - Fixes tangency-labs/solidcore#1469.
